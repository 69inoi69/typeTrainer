# Code rules

How the code is written: the stack, the rules every part follows, and
comments. How the parts fit together is in `docs/HOW-THE-CODE-WORKS.md`.

## Stack (do not change without asking)

- Backend: Go 1.25+, **standard library only** (`net/http`), no frameworks, no
  third-party modules. The single exception: the PostgreSQL driver
  (`github.com/jackc/pgx/v5`), used only through the standard `database/sql`.
  Ask before adding any other module.
- Frontend: plain HTML + CSS + vanilla JavaScript. **No frameworks, no npm,
  no build step.** Files in `web/` are served by the Go server. "No npm" is
  about the app: Node is allowed in `tools/` and CI (browser tests,
  latency measuring), never in what the app serves.
- Storage: behind the `storage.Store` interface. `MemoryStore` by default,
  `PostgresStore` when `DATABASE_URL` is set. Both pass the same tests
  (`internal/storage/store_test.go`); a new `Store` method needs both and a
  test there. Table changes go into a new numbered file in
  `internal/storage/migrations/`, never into an old one.
- Four languages: English, Polish, Ukrainian, Russian. Language data lives in
  `data/` (`languages.json`, `layouts/`, `langs/<id>/words.txt`), not in code.
  **Only English is shown for now:** Polish, Ukrainian and Russian are
  `"hidden": true` in `languages.json` until the English version is
  polished; their data stays and keeps passing the tests.
- Development machine: Windows, PowerShell.

## Architecture rules

- `internal/engine` is pure logic: it must not import anything about HTTP,
  JSON handlers or databases.
- All data access goes through `storage.Store`.
- Every tunable number lives in `internal/config/config.go`. No magic numbers
  in the logic.
- All API routes start with `/api/v1/`.
- Keyboard layouts are data (`data/layouts/*.json`), not code.
- Keep keypress handling in `web/typing.js` light: only flip classes on the 1-2
  letters that changed. The only layout read is the caret position, done once
  per animation frame (`requestAnimationFrame`). Animations use CSS transitions
  or the Web Animations API (`element.animate`), never JS timers. Typing
  latency is the product: measure it after touching this path (`AGENTS.md`,
  rule 4 of "Current phase").
- The frontend is native ES modules with a three-layer import rule
  (`docs/HOW-THE-CODE-WORKS.md`, checked by `webmodules_test.go`): imports only go down, no
  cycles. State shared by several modules lives in the object `S`.
- Every API route except `/languages` and `/auth/*` takes `?lang=`; every
  `Store` method takes the user id and the language id. Each user has their
  own progress in each language; a request without a login is this
  browser's guest (cookie `tt_guest`, `storage.IsGuest`). Password and token
  handling lives in `internal/auth` (standard library only); never store a
  password or a login token itself, only its hash.
- Visual rewards (the foil, the wave along the letters, bumps, toasts) live in `web/fx.js` and must never
  change what is measured or sent to the server. Tab starts a new round, as
  on Monkeytype: the dropped round is not saved, its presses already sent
  stay learned.
- Every text the user sees follows `docs/TEXT-RULES.md` and lives in
  `web/i18n.js`; decide yourself what text a new feature needs. Only the
  English texts exist while only English is shown; the other languages'
  texts are written from them when those languages come back. Never
  hard-code interface text in the other `.js` files or `index.html`; use
  `t("key")` or `data-i18n="key"`. The one exception is `web/file-check.js`
  (the page opened from disk, where modules cannot load).
- Word lists are generated by `tools/wordlists/build.py` (Python, a data tool,
  not part of the app), Freetype's long list (`free.txt`) by
  `tools/wordlists/free.py`, the sentences by `tools/sentences/build.py`.
  Change the block lists and rerun the script instead of editing the lists
  by hand: the next rerun would undo a hand edit.
- The app runs in two ways from the same code: a normal server (`main.go`)
  and WebAssembly on GitHub Pages (`main_wasm.go`). Shared setup goes in
  `setup.go`. Do not add anything that only works with a real server (files on
  disk, background goroutines tied to HTTP) without telling me.
- Comments follow "Comments" below.

How the parts fit together: `docs/HOW-THE-CODE-WORKS.md`.

## Comments

Comments in this repository are written for **a newcomer who knows a little
programming but not this project**: a new contributor, a reviewer, or
the author a year from now. A comment should let that person understand a
part of the code without reading everything around it, and change it safely.

The rules come from the official Go guide to doc comments, the Google
JavaScript style guide, and Ellen Spertus' "Best practices for writing code
comments" (Stack Overflow blog), adapted to this project. Links are at the
end.

For now the code carries only orientation comments: one line at the top of
a file saying what it is, and section dividers (`// ---------- name
----------`). The owner writes the other comments himself, file by file, by
these rules; an agent adds none beyond these.

### The ten rules

1. **Explain why, not what.** The code already says what it does. A comment
   adds what the code cannot say: the reason, the trade-off, the thing that
   was tried and did not work.

   ```go
   // Bad:  i++ // add one to i
   // Good: a held key repeats every ~30 ms: those are not finger movements,
   //       so a repeat is ignored (otherwise "ll" would look super fast).
   ```

2. **Every file starts with what it is for and how it connects.** One short
   paragraph at the top: what this file is responsible for, who calls it,
   and what it calls. In Go, the package comment (`// Package engine ...`)
   says it once per package; each other file gets one line or two if its
   part is not obvious from the name. In JavaScript, each module states its
   job and its layer (see the import rule in `docs/HOW-THE-CODE-WORKS.md`).

3. **Every exported name has a doc comment** that starts with the name and is
   a full sentence (Go convention, read by `go doc`): `// Portion builds ...`.
   Say what it returns in the "nothing yet" and zero cases if that is not
   obvious.

4. **Numbers get a unit and a reason.** `120 // ms: shorter feels like a
   flicker`. Every tunable number lives in `internal/config/config.go` (or
   `web/feel.js` for the feel of the interface), and its comment says what
   happens when it goes up or down.

5. **Mark the extension points.** Where someone will likely add something,
   say how, in one line that starts with "To add":

   ```go
   // To add a route: a handler method here, one line in routes(), and a
   // row in the API table of docs/HOW-THE-CODE-WORKS.md.
   ```

   Only where it really helps: an extension point, not every function.

6. **Explain the surprising, not the ordinary.** Unusual code (a workaround,
   a browser quirk, an order that matters, a lock) always gets a comment.
   Ordinary code (a loop over a slice, a getter) does not.

7. **Point to the source of an idea.** A formula, an algorithm, a borrowed
   trick: name where it comes from (a section of `docs/HOW-THE-MODES-WORK.md`, a
   paper in `docs/thesis/01-existing-systems-and-literature.md`, a link).

8. **Keep comments true.** A wrong comment is worse than none. When the code
   changes, its comments change in the same commit. If a comment is hard to
   write, the code is probably too complicated: simplify the code first.

9. **Plain English, short sentences.** No jargon without an explanation,
   no abbreviations a newcomer would not know. Full sentences for doc
   comments; short fragments are fine at the end of a line.

10. **Nothing that belongs in git.** No author names, dates, "changed by",
    or commented-out code. Unfinished work is marked `TODO:` with what is
    missing and why it is not done yet.

### What goes where

| What | Where |
|---|---|
| What the whole program does, how to run it | `README.md`, `CONTRIBUTING.md` |
| How the parts fit together, the API | `docs/HOW-THE-CODE-WORKS.md` |
| How the three modes work, the formulas | `docs/HOW-THE-MODES-WORK.md` |
| Rules for interface text | `docs/TEXT-RULES.md` |
| What the product is and its decisions | `docs/PRODUCT.md` |
| How the screen looks and behaves | `docs/DESIGN-RULES.md` |
| What a package or module is for | its package comment / the top of the file |
| Why a piece of code is the way it is | a comment next to it |
| What changed and when | the commit message, not the code |
