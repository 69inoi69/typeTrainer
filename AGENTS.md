# Project rules for AI agents

## What this is

An adaptive touch-typing trainer: the practical part of my engineering thesis
(Lublin University of Technology, due 2027). It should look and feel like
Monkeytype, but teach: it tracks each letter's mistakes and speed and builds
exercises from real words around the user's weak letters.

## Who you are working with

- I am not an experienced programmer. Explain what you changed and why, in
  simple words, after every task. I must be able to defend every part of this
  code in front of a thesis committee.
- Talk to me in Russian. Code, comments, commit messages and docs: English.
- Work in small steps. For anything bigger than one feature, show a short plan
  first and wait for my OK.
- Do not run `git commit` or `git push` unless I ask. I commit myself.
- `main` is protected: changes reach it only through a pull request. When I ask
  you to commit, work in a separate branch, push it and open a pull request;
  I merge it myself. Never push to `main` directly.

## Stack (do not change without asking)

- Backend: Go 1.25+, **standard library only** (`net/http`), no frameworks, no
  third-party modules. The single exception: the PostgreSQL driver
  (`github.com/jackc/pgx/v5`), used only through the standard `database/sql`.
  Ask before adding any other module.
- Frontend: plain HTML + CSS + vanilla JavaScript. **No frameworks, no npm,
  no build step.** Files in `web/` are served by the Go server.
- Storage: behind the `storage.Store` interface. `MemoryStore` by default,
  `PostgresStore` when `DATABASE_URL` is set. Both pass the same tests
  (`internal/storage/store_test.go`); a new `Store` method needs both and a
  test there. Table changes go into a new numbered file in
  `internal/storage/migrations/`, never into an old one.
- Four languages: English, Polish, Ukrainian, Russian. Language data lives in
  `data/` (`languages.json`, `layouts/`, `langs/<id>/words.txt`), not in code.
- Development machine: Windows, PowerShell.

## Architecture rules

- `internal/engine` is pure logic: it must not import anything about HTTP,
  JSON handlers or databases.
- All data access goes through `storage.Store`.
- Every tunable number lives in `internal/config/config.go`. No magic numbers
  in the logic.
- All API routes start with `/api/v1/`.
- Keyboard layouts are data (`data/layouts/*.json`), not code.
- Keep keypress handling in `web/typing.js` light: only flip classes on the 1-2
  letters that changed. The only layout read is the caret position, done once
  per animation frame (`requestAnimationFrame`). Animations use CSS transitions
  or the Web Animations API (`element.animate`), never JS timers.
- The frontend is native ES modules with a three-layer import rule (top of
  `web/state.js`, checked by `webmodules_test.go`): imports only go down, no
  cycles. State shared by several modules lives in the object `S`.

- Every API route except `/languages` and `/auth/*` takes `?lang=`; every
  `Store` method takes the user id and the language id. Each user has their
  own progress in each language; a request without a login is the guest,
  `storage.LocalUser`. Password and token handling lives in `internal/auth`
  (standard library only); never store a password or a login token itself,
  only its hash.
- Visual rewards (confetti, bumps, toasts) live in `web/fx.js` and must never
  change what is measured or sent to the server. Tab never restarts an
  exercise: that is a deliberate product decision.
- Every text the user sees lives in `web/i18n.js`, in all four languages
  (en, pl, uk, ru). Never hard-code interface text in the other `.js` files or
  `index.html`; use `t("key")` or `data-i18n="key"`. The one exception is
  `web/file-check.js` (the page opened from disk, where modules cannot load). Finger names there are in the form the
  hint sentence needs (Polish/Ukrainian/Russian instrumental case).
- Word lists are generated by `tools/wordlists/build.py` (Python, a data tool,
  not part of the app). Change the block lists and rerun it instead of editing
  `words.txt` by hand, so the thesis can describe how the lists were made.
- The app runs in two ways from the same code: a normal server (`main.go`)
  and WebAssembly on GitHub Pages (`main_wasm.go`). Shared setup goes in
  `setup.go`. Do not add anything that only works with a real server (files on
  disk, background goroutines tied to HTTP) without telling me.

Details: `docs/ARCHITECTURE.md`.

## Product decisions (do not change without asking)

- **Real words only.** No generated letter combinations like keybr.
- **Two modes and a test.** *Learning* is the adaptive trainer: all the
  algorithm work lives there, with no difficulty switches (the algorithm
  decides what to practise). *Free practice* draws words evenly from the whole
  list, has its own history and never feeds the letter model
  (`internal/freeplay`). It opens when every letter is unlocked, or after the
  one-time *typing test* (one 30-word round at 30 WPM and 97% accuracy). No
  self-declared skill level: the test is the only early way in.
- **Where the work goes (2026-10).** Learning is the main focus until the
  defense: the algorithm, word choice and how learning looks and feels.
  Free practice is a deliberately minimal, separate mode (a future
  Monkeytype-like mode with its own statistics) and grows only after the
  defense. The typing test is provisional and will likely change. Keep the
  two modes apart: nothing in free practice may touch learning data.
- **Everyone starts from the first letters.** No "open all letters" in the
  interface: experienced typists unlock the rest quickly by typing well.
- **The math in `internal/engine/model.go` is the core of my thesis.** Do not
  change formulas or parameter values on your own. If you think something
  should change, explain it and ask.
- If the algorithm's behaviour changes, update `docs/ALGORITHM.md` and the tests
  in the same task. The docs must always describe what the code really does.

Details: `docs/ALGORITHM.md`.

## Not now

Leaderboards, public profile pages, more languages, themes, frameworks.
(Accounts exist: sign up / log in / log out on the normal server, kept in
PostgreSQL when it is configured.) Structure code so they can be added later, but do not build them.

## Commands

```
go run .            # start the server (address in internal/config/config.go)
go test ./...       # run all tests
gofmt -w .          # format
go vet ./...        # static checks
```

Every pull request runs gofmt, vet, the tests and the WebAssembly build
(`.github/workflows/tests.yml`). Every push to `main` runs the tests again and
republishes GitHub Pages (`.github/workflows/pages.yml`). If that run fails,
the site stays on the old version.

## Before you say a task is done

1. `gofmt -w .`, `go vet ./...` and `go test ./...` all pass.
2. New engine logic has unit tests, including edge cases (no data yet, zero values).
3. Docs updated if behaviour or the API changed.
4. A short summary for me: what changed, which files, how to check it in the browser.
